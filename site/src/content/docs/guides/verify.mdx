`twin verify` rebuilds the reporter's environment like [replay](../replay/), applies your fix, reruns the command and reports whether the captured failure is gone. With `--patch`, nothing has to be pushed first.

## Two ways to supply the fix

<Tabs>
<TabItem label="A local patch">

Write the fix in your clone, export it as a unified diff, verify:

```sh
git diff > fix.patch
twin verify twin-capsule.json --patch fix.patch
```

The sandbox checks out the capsule's commit, applies the reporter's working-tree diff, then applies your patch with `git apply`. Make the patch against the capsule's commit.

</TabItem>
<TabItem label="A pushed commit">

Check a fix branch or a PR head instead. `--ref` takes a full commit SHA; `--repo` points at a fork:

```sh
twin verify twin-capsule.json --ref <full-commit-sha>
twin verify twin-capsule.json --ref "$(git rev-parse HEAD)" --repo https://github.com/you/project
```

With `--ref`, the capsule's working-tree diff is not applied: the commit is taken as the whole tree.

</TabItem>
</Tabs>

The capsule can be a file path or an `https://` URL, such as the issue attachment itself. Pass exactly one of `--patch` and `--ref`; twin exits with status 2 otherwise. The capsule must record a failure (`the capsule recorded a passing run; there is no failure to verify a fix for`).

The recorded transcript's header reads `Replay on solari`; the current code prints `Verify on solari` for verify runs. It was also recorded before the check described next was added: verify now runs the command once without the fix first, so the same run would show one more machine.

## The run without the fix comes first

Before it applies your fix, `twin verify` runs the command once on its own machine, exactly like a replay of the capsule. If that run does not fail the way the capsule recorded, the verdict is `INCONCLUSIVE` and the fix is never tried, because a passing run with the fix would prove nothing.

The usual reason is a failure that replay cannot copy. Replay installs dependencies from the repository's lockfile, so a failure that appears only on a fresh install (a newer transitive package, for example) passes here. Use [`twin bisect`](../bisect/) for that kind of failure: it applies the package versions the capsule recorded.

```text
INCONCLUSIVE: the failure did not reproduce without the fix (it passed), so the fix cannot be verified. Replay installs from the lockfile; for a failure that needs freshly resolved dependency versions, use twin bisect.
```

The extra run costs one more machine and about as long as one replay attempt plus setup.

## Verdicts

| Verdict | Meaning | Exit |
|---|---|---|
| `FIXED` | The command passes in the reporter's environment with the fix applied. | 0 |
| `STILL FAILING` | The fix does not change the captured failure. | 1 |
| `DIFFERENT FAILURE` | With the fix it still fails, but differently. | 1 |
| `FLAKY` | Attempts disagreed with each other. | 1 |
| `INCONCLUSIVE` | The failure did not reproduce without the fix, setup failed (does the fix apply?) or an attempt timed out. | 1 |

A patch that does not apply fails the `apply candidate fix` step, which makes the run `INCONCLUSIVE` and prints `git apply`'s error.

## Options

| Option | Default | What it does |
|---|---|---|
| `--patch <file>` | | Unified diff applied on top of the capsule's tree. |
| `--ref <sha>` | | Check out this commit instead (for example a fix branch). |
| `--repo <url>` | the capsule's remote | Clone from here (forks); use with `--ref`. |
| `--attempts <n>` | `3` | Runs of the command. |
| `--env <NAME=value>` | none | Value for a variable the capsule recorded by name only. Repeatable. |
| `--timeout <minutes>` | `15` | Maximum time per attempt. |
| `-v, --verbose` | off | Stream the sandbox's output. |
| `--json` | off | Machine-readable report on stdout. The `verdict` field uses replay's names, so `FIXED` is `not-reproduced`. |
| `--comment <file>` | | Also write a Markdown pull request comment to `<file>`. |

Exit status: `0` fixed, `1` otherwise, `2` usage error.

<Aside>
`FIXED` means the captured command passes in the captured environment. It says nothing about other tests or other environments. For the echarts fix, the patch was also run locally under seven time zones before verifying.
</Aside>

## A comment for the pull request

`--comment <file>` also writes the verdict as Markdown, ready to post on a PR:

```sh
twin verify https://github.com/user-attachments/files/<id>/twin-capsule.json \
  --ref "$(git rev-parse HEAD)" --comment verdict.md
gh pr comment --body-file verdict.md
```

The comment has a headline (for example `✅ FIXED in the reporter's environment` or `❌ STILL FAILING in the reporter's environment`), a table with the command, the reporter's environment, the checked commit, how many attempts passed and a link to the capsule, and the full log in a collapsed section. It starts with a hidden `<!-- twin-verify verdict=… -->` marker so a CI job can find and update its own comment.

## In CI

The [GitHub Action](../github-action/) runs `twin verify <capsule> --ref <PR head sha> --repo <PR head repo>` on pull requests that close an issue with a capsule attached, and comments the verdict on the PR.
