`twin replay` rebuilds a capsule's environment on a fresh Solari sandbox (same runtime, package manager and lockfile, same commit and diff, same environment values and time zone), runs the command, and reports whether the failure reproduces.

## Before you start

- Node 22 or newer.
- A Solari key in the environment. Get one at [console.getsolari.com](https://console.getsolari.com):

  ```sh
  export SOLARI_API_KEY=slr_live_...
  ```

- The capsule: a file path, or an `https://` URL such as the issue attachment link. Before replaying, `twin inspect` shows what it contains without any key:

  ```sh
  twin inspect twin-capsule.json
  twin inspect https://github.com/user-attachments/files/<id>/twin-capsule.json
  ```

## Run it

```sh
twin replay twin-capsule.json
```

Progress goes to stderr as each step starts (`twin: install node 22.23.3`, `twin: attempt 1/3`, …). The report goes to stdout. The echarts replay, recorded on Solari:

```text
Replay on solari (machine AlDq8esMs1x4vuzv…, run fd0c959a)
  ✓ prepare workspace  0.3s
  ✓ install node 22.23.3  2.1s
  ✓ check out 984bf46b2f90  4.5s
  ✓ install npm 10.9.9  3.7s
  ✓ install dependencies (npm ci)  46.4s

Attempts
  1  FAIL exit 1  exit1:0aee0834ac9c4d2d  8.0s
  2  FAIL exit 1  exit1:0aee0834ac9c4d2d  1.7s
  expected  FAIL exit1:0aee0834ac9c4d2d

REPRODUCED: every attempt failed exactly as the capsule recorded.
```

That run used two attempts. The default is three.

## Reading the verdict

| Verdict | Meaning | What to do next |
|---|---|---|
| `REPRODUCED` | Every attempt failed exactly as the capsule recorded. | Keep the machine (`--keep`) and open a shell, bisect against a passing capsule, or verify a fix. |
| `DIFFERENT FAILURE` | It fails here, but not the way the capsule recorded. | Compare the "Key lines here" and "Key lines in capsule" sections the report prints. Often a missing environment value (see Notes) or a runtime that formats the error differently. |
| `NOT REPRODUCED` | The same versions pass on this Linux machine. | The difference is likely in what replay cannot copy: the OS, variables recorded by name only, untracked local files. Check the Notes; supply values with `--env`. |
| `FLAKY` | Attempts disagreed with each other. | Raise `--attempts` to see how often it fails. |
| `INCONCLUSIVE` | Setup failed or an attempt timed out. | The failed step is marked `✗` with its exit code and the last 30 lines of its output. See [Troubleshooting](../../reference/troubleshooting/). |

When attempts do not match the capsule, the report also prints the key lines from the first mismatching attempt next to the key lines in the capsule, so you can see what changed.

### Notes

After the verdict, twin lists differences between the reporter's machine and the replay that it could not remove. The messages look like this (names and counts vary):

- `Captured on darwin (macos); replayed on Linux with the same versions.`
- `3 variables were set on the reporter's machine with unknown values and are left unset (API_URL, DATABASE_URL, SENTRY_DSN). Provide any that matter with --env NAME=value.`
- `2 untracked files existed on the reporter's machine (names only, not recreated).`
- `The diff was scrubbed for secrets and may not apply cleanly.`
- `Overridden with --env, so this replay differs from the capsule in: TZ.`

## Options

| Option | Default | What it does |
|---|---|---|
| `--attempts <n>` | `3` | Runs of the command. More than one separates reproducible failures from flaky ones. |
| `--keep` | off | Keep the machine running at the failure when the verdict is `REPRODUCED` (then: `twin shell`). |
| `--repo <url>` | the capsule's remote | Clone from here instead: a fork, a mirror, or a remote the capsule does not name. |
| `--ref <sha>` | the capsule's commit | Check out this commit instead. Skips the capsule's working-tree diff. |
| `--env <NAME=value>` | none | Value for a variable the capsule recorded by name only. Repeatable. Also overrides recorded values. |
| `--timeout <minutes>` | `15` | Per-attempt limit. An attempt that hits it is killed and the verdict is `INCONCLUSIVE`. |
| `-v, --verbose` | off | Stream the sandbox's output (setup and command) to stderr. |
| `--json` | off | Machine-readable report on stdout. |

Exit status: `0` reproduced, `1` anything else, `2` usage error.

## Supplying values with `--env`

A capsule records most variables by name only. If replay notes that a variable was set with an unknown value and you think it matters, give it one:

```sh
twin replay twin-capsule.json --env API_URL=http://localhost:3000 --env FEATURE_X=1
```

`--env` also tests a hypothesis. On the first live check, a time-zone bug replayed as `REPRODUCED`, and the same capsule with `--env TZ=UTC` was `NOT REPRODUCED`, as expected.

## Replaying a fork or a different commit

The sandbox fetches one commit by SHA from the capsule's `origin` remote. If the reporter's commit only exists on their fork:

```sh
twin replay twin-capsule.json --repo https://github.com/reporter/project
```

To replay the captured environment against a different commit (for example, current `main`), pass its full SHA with `--ref`. The commit is fetched by SHA, which GitHub and GitLab allow for full SHAs. The capsule's uncommitted diff is not applied in that case, since it was made against the captured commit.

```sh
twin replay twin-capsule.json --ref "$(git rev-parse origin/main)"
```

## Keeping the machine

```sh
twin replay twin-capsule.json --keep
```

When the verdict is `REPRODUCED`, the machine stays up and the report ends with:

```text
The machine is still running at the failure, in the reporter's environment:
  twin shell <id>         open a terminal on it
  twin shell <id> --web   get a browser terminal link to share
It is billed while running and released after 15 minutes idle, or now with: twin gc
```

For any other verdict the machine is released as usual. See [Shell](../shell/).

<Aside type="caution">
A kept machine is billed until it has been idle for 15 minutes, or until `twin gc`. Release it when you are done.
</Aside>

## JSON output

`--json` prints the full report on stdout: `verdict` (`reproduced`, `different-failure`, `not-reproduced`, `flaky` or `inconclusive`), `runId`, `backend`, `machineId`, `kept`, `expected` (outcome, signature, key lines), `steps` (id, title, ok, optional, duration, exit code, output tail for failed steps), `attempts` (exit code, timed out, duration, outcome, signature, key lines) and `notes`. Progress still goes to stderr, so stdout stays parseable.
