Coding agents can't fix bugs they can't reproduce. twin gives them the reporter's machine.

`twin mcp` is an [MCP](https://modelcontextprotocol.io) server over stdio, built on the official `@modelcontextprotocol/sdk`. It lets an agent replay a capsule, keep the reproduced failure running, run commands and write files in the reporter's environment, verify its final diff there, and release the machine when it is done.

## Setup

The server needs `SOLARI_API_KEY` in its own environment (get one at [console.getsolari.com](https://console.getsolari.com)). Only `inspect` works without it.

<Tabs>
<TabItem label="Claude Code">

```sh
claude mcp add twin -e SOLARI_API_KEY=slr_live_... -- npx -y @crypticsaiyan/twincli mcp
```

</TabItem>
<TabItem label="Cursor and others">

Add to the client's MCP configuration (for Cursor, `.cursor/mcp.json` or the global settings):

```json
{
  "mcpServers": {
    "twin": {
      "command": "npx",
      "args": ["-y", "@crypticsaiyan/twincli", "mcp"],
      "env": { "SOLARI_API_KEY": "slr_live_..." }
    }
  }
}
```

</TabItem>
</Tabs>

Node 22 or newer must be on the `PATH` the client uses to start the server.

## Tools

A `capsule` argument is a local path or an https URL, such as a GitHub issue attachment (`https://github.com/user-attachments/files/…/twin-capsule.json`), so the agent can start from the issue link alone.

| Tool | What it does |
|---|---|
| `inspect` | Summary of a capsule, or every difference between two. Offline, no key. |
| `replay` | Rebuild and rerun. Returns the verdict, the failure signature and, when the failure reproduced and `keep` is true (the default), the machine id. |
| `run` | Run a shell command line (bash) on a kept machine in the reporter's environment. Returns exit code and the last 200 lines of output. |
| `write_file` | Write a file on a kept machine. Relative paths resolve against the failing command's working directory. |
| `verify` | Fresh machine, apply the fix (a diff, or a pushed commit), report `FIXED`, `STILL FAILING` or `DIFFERENT FAILURE`. |
| `bisect` | Minimal environment difference between a failing and a passing capsule. |
| `release` | Kill one kept machine, or every twin machine when no id is given. |

Arguments and defaults are in the [MCP reference](../../reference/mcp/). Tool results are the same text reports the CLI prints. Failures come back as tool errors starting with `twin:`, so the agent can read them and adjust. `replay`, `verify` and `bisect` send progress notifications while they run.

## Long tool calls and client timeouts

`replay` and `verify` take about 70 seconds or more (most of it installing dependencies), and `bisect` longer. Some MCP clients give up on a tool call before that. twin sends progress notifications during these calls, which lets clients that reset their timeout on progress keep waiting. In Claude Code, raise the timeout with the `MCP_TOOL_TIMEOUT` environment variable, in milliseconds:

```sh
MCP_TOOL_TIMEOUT=600000 claude
```

## The agent loop

<Steps>

1. **`replay`** the capsule with `keep` (the default). A `REPRODUCED` verdict comes back with a machine id.
2. **`run`** commands on that machine to explore: read the failing test, print versions, rerun the command with extra logging.
3. **`write_file`** to try a fix directly in the reporter's environment.
4. **`run`** the failing command again. Iterate on 2 to 4 until it passes.
5. **`verify`** the capsule with the final diff as `patch`. This uses a fresh machine, so leftover state from exploration cannot make it pass.
6. **`release`** the kept machine.

</Steps>

<Aside type="caution">
Kept machines bill until 15 minutes idle or until `release`. Tell the agent to release when it is done. As a backstop, when the MCP session ends the server releases the machines that session kept. `release` with no arguments kills every twin machine on the account, including ones kept from a terminal, each kill confirmed.
</Aside>

A prompt that sets this up:

```text
Issue: https://github.com/apache/echarts/issues/21538
Capsule: https://github.com/user-attachments/files/<id>/new-york.json

Use the twin tools. Reproduce the failure with replay before changing anything,
work on the kept machine with run and write_file, verify your final diff with
verify, then release the machine. Report the verdicts you got.
```

An agent can now open a PR with that diff and say, truthfully, that it reproduced the failure and verified the fix in the reporter's environment. The [GitHub Action](../github-action/) checks that claim again on the PR.

## What the agent can and cannot touch

- Commands and files run inside the Solari sandbox, never on the machine running the MCP server.
- The sandbox receives the capsule's recorded values and any `env` the agent passes to `replay`, nothing from the server's own environment. `SOLARI_API_KEY` stays with the server.
- Kept machines are root shells on your Solari bill. Treat the `run` tool like giving the agent a terminal on a disposable VM.
- When only one twin machine is running, `run` and `write_file` can omit `machine`. With several, any unique prefix of the id works.
